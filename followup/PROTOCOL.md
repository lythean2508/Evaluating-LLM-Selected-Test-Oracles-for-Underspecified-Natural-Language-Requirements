# Model size and frozen rules evaluation protocol

The six FastAPI requirement pairs in the original pilot are the development sample for the existing text rules. The model-size comparison repeats the original controlled and API pilots with Qwen2.5-0.5B-Instruct and Qwen2.5-7B-Instruct. Both use Q4_K_M, llama.cpp b5046, the original prompts, grammars, samplers, seeds, candidate order and scoring. The API comparison rescores the same original and mutant responses. The original archived 0.5B outputs provide a replay cross-check.

The rule baseline is the `rule_agrees` implementation and its `STATUS` and `ANCHORS` constants from commit `400ba16c717231aaccb562422e7a749aac3fa64b`. Preserve the entire `api/restest-extension/design.py` and `controlled/study.py` byte-for-byte. The follow-up runner verifies their SHA-256 hashes before inference or scoring.

## Held-out API requirements

Use the TodoApp service from RESTestBench commit `4decc1e36ea3dd41b64ce3e3ac6a85bc72df36ae`. Its requirement pairs were excluded from the original FastAPI development sample. Review TodoApp IDs in ascending order. Include the first six distinct HTTP method–route pairs that have a precise and vague requirement, are about ordinary task retrieval, creation, modification or deletion, can be described in one fixed fixture, and have a request outcome to which a status-class check can apply. Use the first eligible pair per route and method. Record exclusions before the sixth inclusion. Skip authentication, authorization, reset, and security requirements. Assign support labels and rationales from the visible texts before running either model and before applying the rules.

Every held-out prompt presents the same status candidates in this order: `http_200`, `http_400`, `http_401`, `http_403`, `http_404`, `http_422`, `success`, `denied`. The menu is the intersection of the existing assertion vocabulary and status checks applicable to every fixture. Some status codes and body obligations are outside this menu. Generic 2xx or 4xx is supported when the visible requirement and scenario call for successful completion or client-side rejection. Exact codes need explicit support in the requirement. Use the API contract as interface context, with the same prompt template as the pilot. Score the candidates using requirement support without using an execution result as an annotation input. The transfer evaluation measures support, coverage, and retention on unseen requirement texts. Mutant outcomes are measured on the original FastAPI cohort using its recorded executions.

Compare LLM-only, frozen rules, and intersection for each variant and each model. Count supported assertions selected by the LLM and lost by the gate, supported coverage, unsupported assertions, and empty selections. Report paired counts by requirement, variant and seed. The deterministic baseline runs once per pair and variant. Report repeated seeds as repeated evaluations and describe the held-out labels as a single annotation set unless independently reviewed. This split tests transfer to another service without tuning the rules on its requirements. It does not establish that an upstream requirement was absent from either model’s training data.
